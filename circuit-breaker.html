Que es el Circuit Breaker?

El Circuit Breaker (cortocircuito) es un patron de arquitectura que actua como intermediario entre un servicio que llama (caller) y un servicio destino (callee). Su proposito es detectar fallos y evitar que se propaguen en cascada por todo el sistema.

Funciona de forma analoga a un fusible electrico: cuando detecta una sobrecarga (fallos consecutivos, timeouts), "abre" el circuito para detener el flujo de peticiones hacia el servicio que esta fallando. A diferencia de un fusible fisico, este se puede restaurar automaticamente cuando el problema se resuelve.

Fue popularizado por Michael Nygard en su libro "Release It!" (2007) y es ampliamente utilizado en arquitecturas de microservicios por empresas como Netflix, Amazon y Google.

El Problema: Fallos en Cascada

En sistemas distribuidos, las llamadas a servicios remotos pueden fallar por fallos transitorios: red lenta, timeout, servicio sobrecargado o caido. Sin un mecanismo de proteccion, ocurre una cascada de fallos:

  • Hilos bloqueados: Cada peticion fallida mantiene un hilo esperando hasta el timeout (30s, 60s...). Miles de usuarios = miles de hilos bloqueados.
  • Agotamiento de recursos: Memoria, conexiones a DB, pools de threads se agotan, afectando a otros servicios que comparten esos recursos.
  • Efecto domino: El fallo de un solo servicio puede tumbar todo el sistema: Servicio A falla → B no puede responder → C tambien cae.
  • Reintentos agresivos: Sin control, los clientes reenvian peticiones continuamente, empeorando la sobrecarga del servicio ya saturado.

Sin Circuit Breaker

Cuando no existe un Circuit Breaker, cada peticion hacia un servicio que esta fallando consume recursos inutil y peligrosamente. Los hilos se quedan esperando timeouts, la memoria se llena y otros servicios sanos comienzan a degradarse.

Sin Circuit Breaker: los fallos se propagan y agotan los recursos del sistema completo.

Con Circuit Breaker

El Circuit Breaker se situa entre el cliente y el servicio. Cuando detecta fallos consecutivos, "abre" el circuito y retorna inmediatamente una respuesta de error o fallback, sin intentar la llamada real. Esto protege al sistema y da tiempo al servicio para recuperarse.

Con Circuit Breaker: las peticiones se bloquean rapidamente y se devuelve un fallback.

Los 3 Estados del Circuit Breaker

El Circuit Breaker funciona como una maquina de estados con tres estados. La nomenclatura viene de los circuitos electricos:

  • CLOSED (Cerrado): Estado normal. Las peticiones fluyen hacia el servicio. El CB mantiene un contador de fallos. Si los fallos superan un umbral configurado, transiciona a OPEN.
  • OPEN (Abierto): El circuito esta "roto". Todas las peticiones fallan inmediatamente sin intentar contactar al servicio. Se inicia un temporizador de espera. Cuando expira, transiciona a HALF-OPEN.
  • HALF-OPEN (Semi-abierto): Estado de prueba. Se permite pasar un numero limitado de peticiones para verificar si el servicio se recupero. Si las pruebas son exitosas → CLOSED. Si fallan → OPEN nuevamente.

Ventajas del Circuit Breaker

  • Prevencion de fallos en cascada: Aisla el servicio defectuoso e impide que su fallo se propague a otros componentes del sistema, protegiendo la estabilidad global.
  • Fallo rapido (Fail-Fast): En lugar de esperar un timeout largo (30-60s), el cliente recibe una respuesta inmediata cuando el circuito esta abierto, liberando hilos y recursos.
  • Recuperacion automatica: El estado HALF-OPEN permite verificar periodicamente si el servicio se recupero, restaurando el flujo normal sin intervencion manual.
  • Monitoreo en tiempo real: El CB actua como punto de observabilidad: tiempos de respuesta, tasa de errores, estado del circuito y alertas en tiempo real.
  • Degradacion controlada (Fallback): Permite devolver respuestas alternativas (cache, valores por defecto) en lugar de errores, mejorando la experiencia del usuario.
  • Proteccion contra sobrecarga: Evita enviar miles de peticiones a un servicio saturado, dandole tiempo para recuperarse en lugar de empeorarlo.

Desventajas del Circuit Breaker

  • Complejidad adicional: Agrega una capa extra de logica al sistema. Gestionar los estados (OPEN, CLOSED, HALF-OPEN), umbrales y temporizadores requiere configuracion y mantenimiento cuidadoso.
  • Dificultad en el testing: Simular escenarios de fallo realistas es complejo. No basta con probar el cierre del circuito, hay que validar multiples respuestas de fallback y transiciones de estado.
  • Ajuste fino de parametros: Calibrar umbrales de fallo, tiempos de espera y numero de reintentos requiere conocimiento profundo del comportamiento del sistema. Valores mal ajustados causan falsos positivos o deteccion tardia.
  • No apto para recursos locales: Este patron esta disenado para recursos remotos. Usarlo para operaciones en memoria o servicios locales agrega overhead innecesario.
  • Requiere infraestructura: Implementarlo correctamente en produccion requiere tecnologias como service mesh (Istio) o librerias especializadas. No es trivial hacerlo "a mano".
  • Latencia al reiniciar: Esperar a que el circuito pase por HALF-OPEN puede introducir retrasos inaceptables en sistemas que requieren recuperacion rapida.

Cuando usar y cuando NO usar

SI usar cuando:

  • Servicios se comunican por red (HTTP, gRPC)
  • Dependes de APIs externas o de terceros
  • Quieres prevenir fallos en cascada
  • Servicios con alta latencia variable
  • Necesitas degradacion controlada
  • Arquitecturas de microservicios

NO usar cuando:

  • Recursos locales en memoria
  • Sustitucion de manejo de excepciones
  • Algoritmos de retry son suficientes
  • Arquitecturas basadas en eventos/colas (ya tienen aislamiento)
  • Recuperacion gestionada por infraestructura (load balancers, service mesh)

Herramientas y Frameworks

  • Resilience4j: Libreria ligera y modular para Java, disenada para Spring Boot. Incluye Circuit Breaker, Retry, Rate Limiter y Bulkhead. Es el estandar actual en el ecosistema Java.
  • Hystrix (Netflix): Fue la libreria pionera para Circuit Breaker en Java. Actualmente en modo mantenimiento (deprecada). Se recomienda migrar a Resilience4j.
  • Spring Cloud Circuit Breaker: Capa de abstraccion de Spring que permite usar Resilience4j o Hystrix de forma intercambiable.
  • Polly (.NET): Para aplicaciones .NET, soporta Circuit Breaker, Retry, Timeout y otras estrategias de resiliencia.
  • Istio: Service mesh para Kubernetes que ofrece Circuit Breaker a nivel de red, sin modificar el codigo de la aplicacion.

@Service public class PaymentService { private final RestTemplate restTemplate; @CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback") public PaymentResponse processPayment(PaymentRequest request) { // Llamada al servicio externo de pagos return restTemplate.postForObject( "http://payment-api/api/payments", request, PaymentResponse.class); } // Metodo fallback: se ejecuta cuando el circuito esta OPEN public PaymentResponse paymentFallback( PaymentRequest request, Throwable ex) { return new PaymentResponse( "PENDING", "Servicio de pagos no disponible. Circuit Breaker vs Retry Pattern

Es importante entender que estos patrones son complementarios, no sustitutos. Se pueden combinar, pero la logica de retry debe respetar las excepciones del Circuit Breaker:

Retry Pattern

  • Reintenta una operacion con la expectativa de que tendra exito
  • Ideal para fallos transitorios breves
  • Puede empeorar una situacion si el servicio esta caido

Circuit Breaker

  • Previene realizar operaciones que probablemente fallaran
  • Ideal para fallos persistentes o prolongados
  • Protege al sistema dando tiempo al servicio para recuperarse

Combinacion ideal: Usar Retry para fallos transitorios dentro del Circuit Breaker. Si los reintentos fallan repetidamente, el CB se abre y detiene los intentos.
