¿Qué es la Idempotencia?

La idempotencia es una propiedad de una operación que garantiza que, sin importar cuántas veces se ejecute, el resultado final será exactamente el mismo que si se hubiera ejecutado una sola vez.

En matemáticas: f(f(x)) = f(x). En software: si procesamos un evento o solicitud dos veces (por error de red, doble clic, reintentos automáticos), la segunda ejecución no debe alterar el estado del sistema más allá de lo que hizo la primera.

Es una técnica fundamental en sistemas distribuidos, APIs REST y procesamiento de pagos para evitar la duplicación de datos y mantener la consistencia.

Idempotencia en el Mundo Real

Botones idempotentes están en objetos del día a día: semáforos peatonales, botones de parada en buses y botones de ascensor. Presionarlos muchas veces no cambia el resultado.

¿Para qué sirve?

  • Garantiza consistencia de datos: Evita la duplicación de registros o transacciones financieras. Un cliente no será cobrado dos veces por la misma compra.
  • Reintentos seguros: En sistemas distribuidos, los fallos de red son comunes. La idempotencia permite que el cliente reintente la misma solicitud sin efectos secundarios indeseados.
  • Mejor experiencia de usuario: Evita errores causados por el "doble clic" en botones de pago o al recargar una página (Patrón Post/Redirect/Get).
  • Sistemas tolerantes a fallos: Permite construir arquitecturas donde un mensaje puede ser entregado más de una vez (at-least-once delivery) sin comprometer la integridad.

¿Qué problema soluciona?

Imagina un sistema de compras: un cliente tiene varios productos en su carrito y hace clic en "Comprar". La red falla justo antes de recibir la confirmación, pero el servidor ya procesó el pago.

Sin idempotencia: el cliente reintenta y se crean dos cobros duplicados.

La Solución: Idempotency-Key

Cada solicitud incluye un identificador único (Idempotency-Key). El servidor verifica si esa clave ya fue procesada. Si ya existe, devuelve el resultado original sin procesar de nuevo.

Con idempotencia: el reintento es seguro, solo existe un registro en la DB.

Idempotencia en APIs REST

En las APIs REST, los métodos HTTP tienen diferentes niveles de idempotencia por naturaleza. POST no es idempotente, por lo que requiere un header Idempotency-Key como estrategia adicional.

Patrón Post/Redirect/Get (PRG)

Este patrón convierte una operación POST en un GET idempotente. Tras procesar el formulario, el servidor redirige al navegador a una página de confirmación. Si el usuario recarga, solo repite el GET, no el POST original.

Idempotencia con Colas de Mensajes

En sistemas distribuidos, las colas de mensajes pueden entregar el mismo mensaje más de una vez. Cada mensaje tiene un Transaction ID que se verifica contra una base de datos de IDs procesados antes de ejecutar la operación.

¿Cómo implementarlo?

  • 1. Agregar un identificador único a cada solicitud o evento: Idempotency-Key (header en REST) o MessageIdentifier (en eventos de mensajería).
  • 2. Crear una tabla de claves procesadas en la base de datos donde la clave primaria es el IdempotentId, con columnas opcionales de fecha, estado y resultado.
  • 3. Verificar antes de procesar: Si la clave ya existe en la tabla, devolver el resultado almacenado. Si no existe, procesar la solicitud y guardar la clave junto con el resultado.
  • 4. Operación atómica: El proceso de guardar el resultado y registrar la clave debe hacerse en una sola transacción para evitar estados inconsistentes.
  • 5. TTL (Tiempo de vida): Considerar un tiempo de retención de las claves (24h a 7 días) para no crecer indefinidamente la tabla.

¿Cuándo usarlo?

  • En APIs RESTful que procesan pagos, crean órdenes de compra o registran usuarios. Especialmente en operaciones POST.
  • En Sistemas Distribuidos con colas de mensajes (RabbitMQ, Kafka) donde un mensaje puede entregarse "al menos una vez" (at-least-once delivery).
  • En Pasarelas de pago como Stripe o PayPal, donde cada cargo debe tener un ID único de transacción.
  • En Sistemas con Event Sourcing donde los eventos se reproducen y no deben generar efectos duplicados.
  • En cualquier sistema donde un fallo de red pueda causar que una solicitud se repita automáticamente (ej: timeouts con retry).

¿Qué pasa si NO se usa?

  • Cobros dobles: Un cliente es cargado dos veces por la misma compra. Pérdida de confianza y costos de reembolso.
  • Registros fantasma: Datos duplicados en la base de datos que corrompen reportes, métricas y auditorías.
  • Inventario corrupto: El stock de un producto se descuenta más veces de las reales, generando inconsistencias entre pedidos y existencias.
  • Imposibilidad de reintentos: No se pueden implementar reintentos automáticos de forma segura, disminuyendo la tolerancia a fallos del sistema.
  • Sistemas frágiles: Un simple timeout o desconexión momentánea puede desencadenar un bug difícil de rastrear.
